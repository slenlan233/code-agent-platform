# 原代码复用评估

日期：2026-10-25。本文件记录实施前的静态复用评估，范围为两份用户提供的原文档、`app/` 源码，以及 `app.zip` 中的旧代码快照。后续 0.3.0 已按此评估完成共享 Agent 工厂和原工具迁移，并验证真实 MCP、MySQL、Docker 和浏览器流程；当前实现与接入方式见 [原能力迁移与接入](原能力迁移与接入.md)，最终检查见 [平台升级实现与验收](平台升级实现与验收.md)。下文保留评估时的结论，不代表迁移尚未开展。

## 1. 文档指定的目标

《AIcoding_项目.md》6.3 将方案描述为 `LangGraph Agent Workflow + MCP Tool Gateway + GraphRAG + Permission Policy Engine + Hook Engine + Sandbox Runtime + Audit & Metrics`；9.1 明确写“基于 LangGraph 构建显式状态机，不做黑盒无限循环”。《问题追问.md》Q21、Q31、Q32 继续将 LangGraph 定位为任务流转和失败分支的编排层。

因此外层主编排应使用 LangGraph。LangChain 也被列入技术栈，但文档没有要求手写替代 LangChain 的 Agent 循环。结合现有代码，合理实现为：LangGraph 控制业务阶段，LangChain 创建节点内的 Agent，MCP 连接工具服务，后端治理层决定工具能否执行。

目标产品是能对登记项目开展只读分析、提供规范依据、生成明确计划和 Diff、等待审批、在独立环境执行验证、按失败原因处理并保存审计与交付物的研发平台。网页节点时间线只是观测入口；真正的约束是后端身份、模式、范围、审批、预算、测试和恢复状态。

原文档的指标、事故和“已生产运行”叙述不能直接作为本项目实绩。Q32 关于状态类型迁移、Q33 关于 recursion_limit 的说法仍应以官方说明和已完成的本地验证为准，不能照抄实现。

## 2. 旧快照核对结果

`app.zip` 中的旧 `code_agent/agent/code_agent.py` 导入 `langgraph.prebuilt.create_react_agent`，在第 86 行创建预构建 Agent；同文件也使用 LangChain 消息、Prompt 和 RunnableConfig。旧 `code_agent/utils/mcp.py` 已使用 `MultiServerMCPClient`。

旧主助手第 55 行把 `file_tools + shell_tools + terminal_tools + rag_self_tools + browser_tools + vm_tools + mysql_tools` 合并后交给 Agent。旧 `FileSaver.put_writes` 的函数体为 `pass`。

这说明原来的主助手已混合使用 LangChain 组件、LangGraph 预构建 Agent 和 MCP。独立的显式 StateGraph / 多 Agent 示例属于另一种编排尝试。当前 `create_agent`、官方 SQLite saver、环境凭证、入口转发和旧工具开关等，包含前几轮迁移所作的改动，不能全部当作原作者的旧实现评价。

官方目前推荐把 `langgraph.prebuilt.create_react_agent` 迁移到 `langchain.agents.create_agent`：[LangChain v1 迁移说明](https://docs.langchain.com/oss/python/migrate/langchain-v1)。这是构建入口迁移，不意味着原工具失效。

## 3. 复用结论

| 模块 | 判断 | 复用方式 |
| --- | --- | --- |
| 模型和 Agent 创建 | 可以复用 | 保留模型适配与 `create_agent`；统一配置，按角色传入工具、Prompt 和结构化输出；不另写模型工具循环 |
| 原 `code_agent` 顶层运行 | 需要重新组织 | 旧 CLI 负责输入展示，共享 Agent 工厂用于模型节点；项目/任务身份、审批、测试、恢复交由平台流程 |
| 文件工具 | 可保留读取/搜索能力；写入入口需调整 | 固定 `.temp` 改为任务目录；Plan 只提供只读工具；正式修改经过补丁、范围校验、审批和应用入口 |
| Shell | 执行与回收逻辑值得保留 | 超时、输出、退出码、进程树清理可复用；平台测试命令在隔离运行器中执行，不直接复用宿主机任意 Shell 权限 |
| 可见终端 | 保留为本地交互扩展 | 会话、终端 ID、独立日志和串行窗口操作有价值；依赖 Windows 桌面，不承担 CI 或默认 Sandbox 执行 |
| MCP 客户端 | 可以改造复用 | 统一配置、允许工具清单、环境变量、错误与生命周期；有状态会话需保持在适当的异步运行生命周期内 |
| MySQL | 底层连接/事务逻辑可复用 | 参数值绑定、rollback/finally 可保留；查询与管理工具分开，使用受限账号，校验 SQL 类别及标识符 |
| 百炼 RAG | 查询/上传 SDK 封装可复用 | 查询和管理接口分开；参数配置化，返回来源/版本/范围，增加超时、限制和脱敏日志 |
| Selenium 百度工具 | 局部复用，优先级较低 | 可保留为特定搜索适配器；不把它视作通用浏览器测试能力，需要独立浏览器会话与稳定的输入输出契约 |
| Lima 工具 | 留作独立实验适配器 | 环境强绑定，不作为文档要求的任务 Sandbox 默认后端 |
| 旧自制 checkpoint | 不建议继续使用 | 旧快照 pending writes 未实现；当前已迁移到官方 saver，保留这项迁移 |

## 4. 具体问题与依据

### 高优先级：全量工具组装没有执行层权限隔离

当前 `app/code_agent/agent/code_agent.py:53` 将全部工具交给同一个 Agent。提示词要求先查 RAG、复用终端、限制失败重试，但不能形成对文件、数据库、上传和宿主机命令的强制约束。

`app/mcp/shell_tools.py:63` 在宿主机启动 PowerShell，`cwd=.temp` 只规定初始目录，无法限制命令访问其他路径。平台应保留执行器中的超时/输出/回收经验，使用新的隔离后端和审批网关；不能把原工具列表原封不动塞入新节点。

### 高优先级：数据库“只读”没有在实现中保证

`app/mcp/mysql_tools.py:198` 的查询工具将任意 SQL 传给 `execute_sql`，没有 SQL 类别判断；连接配置第 14 行为 `user=root`。第 498 行另有任意管理命令接口，且旧助手会加载该 Server 的全部工具。

该文件使用参数占位符绑定插入/更新的值，并有事务回滚和连接关闭，这是可保留的实现。但表名、字段名等仍通过字符串拼接，例如第 169、258、315、370 行；应进行标识符校验和授权，不能把值参数化等同全部 SQL 都已受控。没有 `commit=True` 也不能作为只读权限机制。

### 高优先级：RAG 查询和任意路径上传共用模型工具集

`app/code_agent/rag/rag.py:78` 注册文件上传工具，参数接受绝对路径，并由第 140 行读取文件上传。工具自身没有项目范围校验和审批；旧主助手会加载查询与上传两类工具。Plan 或只读查询应只获得查询工具，上传放到独立管理员流程。

### 中优先级：stdio 日志、错误和输出契约不统一

`app/code_agent/rag/rag.py:66`、第 149 行及上传流程中的多处 `print` 写标准输出；第 246、248 行还打印上传 headers 和 URL。stdio MCP 的协议输出应与诊断日志分离，潜在敏感字段应脱敏。

`app/mcp/browser_tools.py:216` 捕获异常后打印并返回空字符串，使调用方难以区分“没有搜索结果”和“执行失败”。VM 的命令辅助函数只返回 stdout/stderr 字符串，再以是否有字符串判断失败，也会产生歧义。工具统一返回状态、错误、退出码及受限内容，比让模型解析自由文本可靠。

### 中优先级：会话和测量方式不适合项目平台

`app/code_agent/agent/code_agent.py:99` 固定 `thread_id="45"`，不区分用户、项目和任务。第 148 行的工具耗时取两次消息接收间隔，包含模型等其他等待，不能作为真实工具耗时。

第 48–51 行串行加载多个 MCP Server，缺少按工具组降级处理；任一初始化异常会中断整个助手启动。应按任务需要加载，并向用户报告哪些能力不可用。

### 中优先级：浏览器与 VM 环境绑定

`app/mcp/browser_tools.py:18`、第 22 行固定浏览器和用户目录，搜索工具依赖特定百度页面选择器；滚动循环没有明确总时限。它适合本地特定搜索实验，不具备跨任务浏览器隔离和通用测试能力。

`app/mcp/vm.py:17` 固定 `lima-test`，并在多处固定 Windows 下 limactl 的位置；路径通过拼接、拆分传递，带空格的路径容易出错，临时文件固定为目标名加 `.tmp`。共享 VM 与固定临时路径也不提供按任务隔离。可留作可选后端，不应为复用而替代已经实现的 Docker 隔离路径。

## 5. 建议的收拢方式

保留现有 LangGraph 业务状态、权限、审批、产物和 Docker 执行层；将原 Agent 创建逻辑抽成共享工厂，旧 CLI 和平台模型阶段使用同一工厂。原工具以配置化适配器接入：只读文件和百炼查询优先，数据库随后，可见终端/浏览器/VM 按实际场景启用。

所有工具调用都先经过统一网关。旧 Agent 不再自行取得完整工具列表，也不持有绕过平台的宿主机写入入口。持久化由外层任务和官方 checkpoint 管理，避免节点内重复使用旧固定会话和重复保存整套历史。

当前新平台 `Gateway.register_mcp` 只是包装已经加载的工具，平台启动尚未统一装配原 MCP 连接；持久会话的异步生命周期也需要适配。这是尚待补齐的迁移工作，不能把已有接口测试等同真实百炼/MySQL/浏览器接入验收。

复用应以减少维护和保留稳定功能为依据：工具底层逻辑优先复用；与任务身份、权限、审批和隔离相冲突的控制流程需要调整。无需为了保留文件名或几行组装代码而维持两套平行实现。
