# 配置管理与数据库连接

文档编号：JAVA-KB-04｜版本：1.0｜日期：2026-10-27
适用范围：Spring Boot 3.5.x、MySQL，以及当前编程平台生成的 Java 项目。性质：通用配置建议与本平台连接契约；其他项目采用这些变量前先确认其配置。

## 1. 代码如何知道连接哪个数据库

连接方式由代码和配置共同决定。生成代码时，确定配置项名称和读取方式；应用启动时，读取当前环境的 URL、用户名与密码，建立数据库连接。代码不需要包含真实密码。

相同代码可在本地连接开发库，在测试环境连接临时库；这是配置切换，不是把数据从测试库自动转移到开发库。应用重启后能读回数据，前提是仍使用同一个正常业务数据库，并且启动过程没有清表。

## 2. 当前平台的业务数据库契约

当平台管理员已配置本机 MySQL 实例、自动准备可用，且项目需要数据库时，平台可以为该项目准备专属库、应用账号、迁移账号，并将真实连接信息写到项目根目录 `.env`。模型获得变量名称与连接就绪状态等公开契约，业务代码按契约读取；不要求把真实密码加入对话。

这些是当前平台约定，不是 Spring Boot 自带的固定变量名：

| 变量 | 含义 | 使用方 |
| --- | --- | --- |
| `APP_JDBC_URL` | 当前项目业务库的 JDBC URL | DataSource 和 Flyway |
| `APP_DB_USER` | 业务增删改查账号 | DataSource |
| `APP_DB_PASSWORD` | 业务账号密码 | DataSource |
| `MIGRATION_DB_USER` | 该项目库的迁移账号 | Flyway |
| `MIGRATION_DB_PASSWORD` | 迁移账号密码 | Flyway |
| `APP_SERVER_PORT` | 可选 HTTP 端口，示例默认 8081 | Web 服务 |

平台管理配置、生成项目的 `.env`、测试环境变量是不同配置层，不能互相复制混用。已有项目连接配置由项目实际约定决定，不能擅自覆盖。

如果平台返回“数据库未准备”“连接配置变更”或缺少变量，应报告具体缺项并使用配置入口解决，不能编造密码、默认使用 root，或声称数据库已连接。

## 3. Spring Boot 配置映射示例

以下片段放在 `application.yml`，假设进程启动前已经获得对应环境变量：

```yaml
server:
  port: ${APP_SERVER_PORT:8081}

spring:
  datasource:
    url: ${APP_JDBC_URL}
    username: ${APP_DB_USER}
    password: ${APP_DB_PASSWORD}
  flyway:
    url: ${APP_JDBC_URL}
    user: ${MIGRATION_DB_USER}
    password: ${MIGRATION_DB_PASSWORD}
    locations: classpath:db/migration
    clean-disabled: true
  sql:
    init:
      mode: never
```

URL 指向已经创建的项目库，Flyway 负责这个库内的表结构；不要假设 Flyway 会拥有管理整台 MySQL 的权限。使用 JPA 时另外明确 DDL 策略；使用 JDBC 的项目不必引入 JPA。

Spring Boot 支持环境变量、YAML、properties 和命令行等配置源。上面的 `${变量名}` 是配置占位符，不会替你创建真实值。[Spring Boot 外部化配置](https://docs.spring.io/spring-boot/3.5/reference/features/external-config.html)

## 4. `.env` 必须有明确的加载方式

普通 Spring Boot 应用不会因为目录中存在 `.env` 就默认读取它。启动脚本可以采用白名单解析器，将本项目 `.env` 中允许的键注入子进程环境，再启动 Maven 或 Java；也可以由 IDE、容器运行配置或经过配置的外部配置文件提供变量。

解析 `.env` 时要明确支持的语法，不把文件当作 PowerShell/Shell 代码执行。对路径加引号；不输出变量值，不把密码作为进程命令行参数。不要通过修改系统级环境变量解决单个项目的问题。

提交的 `.env.example` 只保留键和空值：

```dotenv
APP_JDBC_URL=
APP_DB_USER=
APP_DB_PASSWORD=
MIGRATION_DB_USER=
MIGRATION_DB_PASSWORD=
APP_SERVER_PORT=8081
```

一个可选 `.gitignore` 片段：

```gitignore
.env
.env.*
!.env.example
target/
```

本地真实 `.env` 与模板用途不同。删除源码、归档项目或修改前端均不要求删除已有数据库连接。

## 5. 只读 MySQL 工具和应用连接的区别

MySQL MCP 查询工具供 Agent 查看被授权的库、表结构或只读数据；它不等于生成后端的 DataSource。不开启只读 MCP，不代表 Java 应用不能持久化：只要业务库配置已准备、代码读取正确且业务账号有 CRUD 权限，应用仍可以正常读写。

反过来，只读工具连接成功，也不能证明生成的应用已经成功迁移或正确写入数据，仍需运行应用与集成测试。

## 6. 测试环境配置

测试建议使用独立的 `APP_TEST_JDBC_URL`、`APP_TEST_DB_USER`、`APP_TEST_DB_PASSWORD`、`MIGRATION_TEST_DB_USER`、`MIGRATION_TEST_DB_PASSWORD`，由 `application-test.yml` 明确映射。它们是建议命名，测试执行器若采用其他契约，应以执行器实际注入的变量为准。

禁止在测试配置缺项时自动回退到正常业务库。测试可以由平台或 Testcontainers 提供临时 MySQL；执行前核对实际主机、库名和隔离生命周期，避免“设置了 test profile 就一定安全”的误解。

## 7. 验证顺序

先验证配置项齐全且不泄露值，再验证目标库可达及账号权限，然后运行迁移和 CRUD 集成测试，最后做本地启动与重启持久化验收。每一步只报告实际观察到的结果。
