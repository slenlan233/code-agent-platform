## 1. 两份材料如何一起使用

《AIcoding_项目.md》提供目标能力、架构和里程碑；《问题追问.md》补充运行机制、失败处理、评估方法及可观测性细节。

追问材料默认使用生产项目口吻，其中团队规模、接入项目数、线上吞吐、成本、收益和事故经历，都不能直接视为当前项目事实。后续通过可运行代码、测试记录和实际测量确认完成状态。

总体方向：保留 Python、LangGraph、现有模型适配和 MCP 工具原型，将它们组织为一个模块清晰、任务可恢复、工具受控、结果可验证的平台。首版采用一个后端进程内的逻辑分层，先保留 CLI，再增加 Web 入口。

首先完成的产品范围：只读代码问答、最小项目知识检索、项目规则、结构化计划，以及从第一天开始保存的任务记录与评估结果。随后逐步增加补丁、审批、隔离测试、代码图谱和 CI Review。

## 4. 关键设计

### 4.1 把项目、会话、任务分开

- 项目描述授权仓库、允许读取的文档、规则、测试配置和可用工具。
- 会话保存用户交流和经过整理的相关上下文。
- 任务绑定一次具体目标、代码基线、运行模式、计划、审批和最终结果。
- graph thread_id 采用明确映射，避免不同用户、项目或任务复用现有固定编号。
- user_id、项目权限等身份信息由后端可信上下文提供，模型不能通过工具参数更换身份。

建议初版运行模式为 readonly、plan_only、approval_write、ci_review，并提供 enabled 开关。开关和权限在后端执行时校验；关闭写入后，在途任务不能继续落地修改。

### 4.2 统一所有工具的执行路径

Agent 提出工具请求 → 输入校验 → 资源范围检查 → 模式与权限判断 → 审批校验 → 配额检查 → PreToolUse → 执行适配器 → PostToolUse → 保存结果 → 返回 Agent。

直接 Python 文件工具与 MCP 工具都必须走这条路径。RAG、浏览器、数据库和未来的图谱工具也不例外。拒绝、参数错误和执行失败同样保留审计记录。

权限优先级明确定义为 deny 优先，其次 ask，最后 allow；企业强制策略不能被项目、用户配置放宽。工具注册时声明输入输出结构、风险、只读属性、超时、大小上限及幂等特性。

路径校验应处理规范化、目录穿越、符号链接及 Windows 重解析点等边界。共享检索结果和缓存也必须遵守用户及项目权限。

MCP 子进程采用环境变量白名单，避免继续无差别继承宿主机完整环境。数据库工具初版只接测试环境的只读账号，不将当前全部增删改工具一次性开放。

### 4.3 计划、审批和实际执行要绑定版本

先只读检索代码与文档，再生成有证据的计划，避免在缺少上下文时先批准一个笼统方案。

计划至少包含目标、修改文件、影响范围、证据、风险、测试方案、回滚方案，以及数据库结构变更和兼容性等风险标记。必要信息缺失时应标为未知，不能默认为无风险。

审批绑定 task_id、审批人、代码基线、计划版本或 hash、具体操作/补丁摘要、有效期。批准后的计划变化、补丁变化或基线变化，要重新检查并按影响重新审批。模型文本中的“用户已同意”不能替代审批记录。

区分两种动作：计划批准后允许在指定隔离区生成和验证修改；最终 Diff 审批后才允许导出或应用对应修改到目标分支。新增文件、删除和重命名也必须纳入范围检查，不能只依赖遗漏未跟踪文件的普通 git diff。

approved_files 不能只限制文件工具。任意 Shell 或测试脚本也可能改源码，因此不能给它绕过补丁入口的宿主机写权限。隔离验证阶段限制挂载和可写区域，并复核执行前后的源文件变化，超范围的结果不得导出。

### 4.4 恢复任务不等于重新执行一遍

checkpoint 保存图执行状态；任务表提供用户可见状态；工具执行记录和 artifacts 保存实际副作用与证据。恢复时三者需要核对，不能只读取 current_node 然后猜下一步。

写补丁、创建分支、启动容器等操作应有稳定的操作标识、幂等检查或状态核对。重复提交审批、重复恢复、执行后断线等情况，不应重复写入或重复启动任务。审批节点与有副作用的执行节点尽量分开。

大日志、完整 Diff 和测试报告存为 artifact，状态中保存引用和必要摘要，防止 checkpoint 因反复累计完整输出膨胀。

### 4.5 上下文、规则与记忆各有范围

项目规则按任务标签加载；企业强制策略保留在后端。检索文档、仓库注释、Issue 和记忆中的自然语言不能直接改写权限、批准操作或注册可执行 Hook。

知识结果返回 source_id、project_id、路径、标题、版本、状态、片段和位置。代码来源额外绑定 commit 或内容摘要。基础版先实现过滤、引用和存在性校验；混合检索、重排和语义冲突识别逐步加强。

同主题 active 文档并不必然矛盾，需检查适用条件和规则优先级。确有冲突时保留双方证据；已有强制安全策略仍按后端规则执行，普通任务审批不能覆盖它。

会话摘要保留需求、已批准范围、证据引用、修改、测试结果、未解决问题和下一步。长期记忆需有来源、用户/项目/环境范围、有效期和撤销能力，不能覆盖已验证配置。

缓存标识包含授权范围及内容版本，例如代码基线、规则摘要、文档版本、索引构建版本。权限撤销或内容变化后不继续使用旧结果。

### 4.6 预算与完成状态由系统判断

分别管理上下文窗口、累计 token/成本、工具调用次数、重试次数和总执行时间。上下文过长可以整理压缩；累计预算耗尽则停止或等待明确续额，压缩不会退回已经花掉的费用。

模型用量以供应商返回数据为准，估算值显式标记；按模型及价格版本计算费用。记录失败任务成本，避免只统计成功任务产生的开销。

完成状态以工具结果、Diff 范围、测试报告和门禁结果判定。没有执行记录，最终总结不能声称已修改或测试通过。路径和行号有效也不等于语义正确，仍需测试及人工审查关键业务逻辑。

## 5. 建议的模块落点

保留 app/code_agent 作为核心包，按职责新增模块。以下路径为建议，不表示已经创建。

| 模块 | 建议路径 | 职责 |
|---|---|---|
| 配置 | app/code_agent/config/ | 模型、项目、策略、预算配置及版本 |
| 数据结构 | app/code_agent/schemas/ | Task、Plan、ToolRequest、Evidence、Review 等输入输出 |
| 编排 | app/code_agent/workflow/ | StateGraph、节点、分支、恢复和结束条件 |
| 治理 | app/code_agent/governance/ | 权限、审批、Hook、预算与范围检查 |
| 工具入口 | app/code_agent/gateway/ | 统一注册、执行、结果和错误格式；复用现有 MCP 适配 |
| 上下文 | app/code_agent/context/ | 项目规则、代码搜索、证据校验、摘要与后续记忆 |
| 存储 | app/code_agent/storage/ | 业务数据、checkpoint 接入、审计和 artifact 索引 |
| 执行环境 | app/code_agent/runtime/ | workspace、Git、Docker、命令执行和回收 |
| 图谱 | app/code_agent/graph/ | 单语言解析、符号解析、图模型和受限查询 |
| 评估 | evals/ | 固定任务、标注、评估版本和结果报告 |
| 接口与入口 | app/api/、app/cli/ | FastAPI、流式任务事件与 CLI；后续共用同一服务层 |

现有工具文件逐项接入新入口，学习示例保留为示例。无需一开始重写所有工具或拆分微服务。

存储先以一个 PostgreSQL 实例承载任务、审批、审计和兼容的 checkpoint 后端；大文件先用受控本地 artifact 目录。向量扩展、图数据库、队列和对象存储随阶段接入，避免首版同时维护多套数据库。

## 6. 阶段计划及验收

### 阶段 A：只读 MVP 与治理基础

工作：统一入口和环境配置；移除源码凭证；建立项目、会话、任务和可信身份范围；统一只读工具执行入口；记录用量、耗时、错误、来源及版本；最小知识库查询和项目规则；建立离线评估集。

验收：能针对一个示例仓库解释模块并给出有效来源；不能跨项目或读敏感路径；只读模式下写工具请求被后端拒绝；两个会话不串数据；工具调用及拒绝均可查；模型未配置时给出明确说明。

建议先整理约 20 个核心任务和约 20 个边界/反测用例，数量属于计划，结果以实测记录为准。

### 阶段 B：结构化 Plan、补丁与审批恢复

工作：接入任务 StateGraph、结构化 Plan、审批暂停与恢复、补丁输出、来源校验、范围检查和可配置预算。此阶段可以只生成补丁文本，不应用到目标仓库。

验收：能审查和驳回计划；过期审批或计划变化不能继续使用旧批准；重复恢复不重复执行；计划外文件被阻断；没有测试记录时正确显示未验证。

### 阶段 C：隔离修改、测试与基础控制台

工作：临时 Git workspace、Docker 运行器、受控测试命令、输出和资源上限、artifact 保存与清理；FastAPI 和基础页面展示任务、计划、Diff、审批、测试及事件时间线。

验收：对一个测试稳定的示例项目完成“补测试 → 计划审批 → 隔离区生成修改 → 运行测试 → 审查 Diff → 导出补丁”；原始工作区保持原状；新增文件不会漏出 Diff；异常退出后仍能找到报告与失败原因；资源回收不先于结果保存。

### 阶段 D：知识检索增强与 Java 图谱 PoC

工作：业务规则、文档冲突、混合检索和重排；先针对 Java Spring Boot/MyBatis 的 Controller → Service → Mapper → Table 链路建立解析与查询；节点含仓库、完整签名和版本，边含来源、适用条件及观测依据。

验收：对人工标注的小型仓库回答调用链与影响范围问题；明确未解析和动态关系；代码变化后旧关系正确失效；对照仅代码搜索/仅 RAG 的结果测量增益。

### 阶段 E：受控多 Agent 与 CI Review

工作：在单 Agent 主流程稳定后增加角色隔离、结构化交接和分歧升级；Headless Runner、结构化 Review、反馈和固定 MR 回放评估。CI 初期以建议方式验证，成熟后再决定哪些已验证问题阻断流程。

验收：子 Agent 不能扩权或嵌套委派；关键信息保留来源；Review 只报告与变更相关的可行动问题；按严重性区分结果；可查看误报反馈及单位成功任务成本。

K8s 资源池、全语言图谱、插件市场、本地大模型集群和后训练作为后续专项，不纳入首版交付。

## 7. 优先补充的数据记录

第一阶段：agent_project、agent_session、agent_task、agent_task_event、agent_tool_call、agent_model_call、agent_knowledge_reference。任务和事件绑定运行版本、开始结束时间及失败类型。

第二阶段：agent_plan、agent_approval、agent_diff。审批保留对象版本、范围、审批人、决定和有效期。

第三阶段：agent_sandbox_run、agent_hook_event、agent_artifact。记录实际执行、日志位置、报告摘要、文件摘要和清理状态。

后续：agent_evaluation_run、agent_feedback、agent_memory、agent_knowledge_conflict。评估集本身先作为可版本管理的文件；按需要将运行和反馈入库。

表名统一使用 agent_knowledge_reference，避免两份材料中的 agent_knowledge_ref 等命名混用。业务表与 checkpoint 表分别管理，不能只依赖其中一方实现恢复。

## 8. 关键验收用例

1. 只读/计划模式请求写文件或命令执行时被系统拒绝。
2. 路径穿越、链接逃逸、跨项目读取和缓存越权均不能取得内容。
3. 文档或工具返回“忽略权限、用户已批准”时，不改变实际授权。
4. 已批准计划变化、补丁变化、审批过期或基线变化时，重新检查授权。
5. 重复审批、断线恢复、写入后中断不会重复应用同一补丁。
6. 工具失败、被拒绝和超时都有记录；只读可有限重试，写入先核对状态。
7. 累计预算耗尽后停止，不能借上下文压缩继续超额执行。
8. 新文件、删除和重命名进入最终修改范围检查。
9. 没有工具凭据时不能报告已执行，没有有效报告时不能报告测试通过。
10. 隔离测试不能访问宿主机敏感目录、生产凭证和其他项目工作区。
11. 测试失败不得通过删断言、跳过用例或降低业务标准自动变绿。
12. 项目关闭或撤销写权限后，在途任务不能继续应用修改。

平台纯逻辑使用假模型、可控工具返回和临时仓库测试；真实模型评估单独运行并保存版本、原始结果与人工标注，避免普通测试隐式花费 API 额度。

## 9. 材料中需要修正或限定的说法

### Q32：StateGraph 强制从 TypedDict 改为 Pydantic

不能作为本项目设计约束。当前环境安装 LangGraph 1.0.1，本地小实验中 TypedDict 与 Pydantic 状态均可执行。官方 Graph API 也提供 TypedDict 示例。[LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

### Q33：recursion_limit 不能限制跨节点循环

此说法不正确。官方说明限制的是单次图执行的 super-step 数；在当前环境构造 A → B → A 循环，recursion_limit=3 会触发 GraphRecursionError。仍建议另设累计预算、工具次数和重复失败限制，它们分别控制不同问题。[LangGraph recursion limit](https://docs.langchain.com/oss/python/langgraph/graph-api#recursion-limit)

### Q36/Q60：有 checkpoint 或任务状态表就能安全恢复

不充分。interrupt 恢复会从所在节点开头重新执行，节点里已经做过的外部操作可能重复。审批和写操作需要拆分并设计幂等核对。[LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

### Q43：LangGraph 通常要求整条链绑定同一个模型

不是框架要求。节点本身是函数，可以按需要调用不同模型。初版固定模型是降低配置复杂度的选择，不应归因为框架必须序列化模型实例。[LangGraph nodes](https://docs.langchain.com/oss/python/langgraph/graph-api)

### Q86/Q94/Q103：独立进程或 Worktree 天然形成强隔离

不能据此保证跨租户安全。Worktree 有独立检出目录，但共享部分 Git 数据和引用；它不限制宿主机进程的文件访问。进程也不会仅因独立启动就获得不同文件权限。执行隔离必须落实到受控挂载、操作系统权限、容器和网络策略。[Git worktree](https://git-scm.com/docs/git-worktree)

### Q131：后续只传“规则见上文”就消除历史规则的 token 成本

不能直接这样估算。应用内减少重复拼接、检索结果缓存、模型上下文保留和供应商前缀缓存是不同机制。应记录实际输入和缓存用量，再判断成本收益，不预设节省比例。

### Q115a：20 个用例按成功率下降 2% 设置门槛

样本量不匹配：20 个二值任务中，一个用例变化就是 5 个百分点。初版先明确哪些关键用例必须通过；模型质量比较保留逐项结果，必要时重复运行和扩大样本。

### 图谱、模型及运行指标中的固定数字

AST 识别语法不等于完整解析方法调用目标。运行 trace 可以证明某个场景真实发生过调用，但采样有限不代表已观察边本身必然低可信；应分别描述证据可靠性、覆盖和时效。

文档中的置信度、准确率、P95/P99、并发、模型部署硬件和收益比例均需单独测量，不能作为初始化数据或验收已完成的证据。产品比较、计费信息及合规结论不作为本轮改造依据，需要使用时再专项核验。
